# 迁移决策规范

## 证据要求

每条迁移计划必须包含：

- `file`：输入项目内的相对路径；
- `issue`：需要解决的问题描述；
- `action`：允许的 `copy` 或 `transform`；
- `impact`：影响面等级；

`transform` 计划必须包含 `evidence`，引用检索命中的范例或文档；
`copy` 计划不要求证据，因为没有修改代码。

没有依据的替换、删除或重写一律禁止。

## 迁移档案约束

- 计划必须符合当前 `migration.profile` 与 `migration.scope`；
- 档案外部的重构类别（如未选框架档案时升级框架）不得自动执行；
- `transform` 使用当前档案的转换规则。

## 影响面分级

- `low`：单文件、局部语法或 API 替换，可自动应用；
- `medium`：涉及文件间依赖或语义调整，需要人工审批；
- `high`：跨模块重构、删除代码或架构调整，必须人工审批。

审批通过前不得应用 `medium` 与 `high` 计划。

## 最小变更

- 每次只处理计划中声明的目标；
- 禁止顺手重构无关代码；
- 禁止跨文件变更，除非计划明确声明并经审批。

## 大规模重构阈值

- 当需要重构的代码量超过输入项目总代码量的 30% 时，必须暂停任务；
- 暂停后向用户说明涉及的文件、代码量与影响面，征得用户明确同意后才能继续；
- 统计口径：计划涉及文件的变更行数之和 ÷ 扫描文件总行数；
- 骨架阶段可先用文件占比代替，后续接入精确的行数统计；
- 该阈值不允许 Agent 自行豁免。

## 预算限制

- 计划条目数、单条重试次数、补丁总数均有上限；
- 预算耗尽时立即终止任务，不得继续尝试。
